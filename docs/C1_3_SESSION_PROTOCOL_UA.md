# Coffeo C1.3 — протокол сесій

Робоча гілка для несумісної зміни: `codex/c1-3-session-protocol`. `dev` пов'язана з Render production, тому цей квиток не можна розгортати туди до узгодженого релізу API/web і перевіреної міграції. Поточний web ще не має browser recovery C1.4: при завершенні access він не зможе автоматично викликати refresh. Код C1.3 сам по собі не є готовим production-релізом.

Нова міграція доповнює Session полями поточної й попередньої генерацій, версією ротації, датою відкликання та індексами; наявні записи не переписує. Legacy JWT без `sid/jti` відхиляється, потрібен повторний вхід. На production міграцію не застосовували. Перед релізом потрібні backup, перевірка canonical email collisions, репетиція на ізольованій БД і парний rollout.

Два входи мають різні `sid/jti`. Refresh перевіряє підпис, алгоритм, тип, аудиторію та строк, блокує рядок Session і змінює його атомарно. Максимальний строк сесії — сім діб від входу. Поточна й попередня генерації в межах 10 секунд повертають однаковий refresh. Старий підписаний токен після цього вікна відкликає сесію. В БД зберігається лише hash токена; відтворений JWT перевіряється проти hash перед поверненням. Секрети access/refresh різні.

Кожен приватний запит перевіряє `revokedAt` та `expiresAt` у БД. Logout відкликає Session, тому старий access не відкриває приватні маршрути. Несправність БД повертає 503 без очищення cookie. Прострочений access із живим refresh повертає `ACCESS_EXPIRED`; оновлення робить тільки `/auth/refresh`. Реєстрація створює User+порожній Profile однією транзакцією; email приводиться до trim/lowercase. Новий пароль — 12–72 символи і не більше 72 UTF-8 байтів; старі паролі приймаються на login.

`tests/c1-3-sessions.test.cjs` використовує синтетичних користувачів і одноразову PostgreSQL в CI. Покриває одночасні входи, два паралельні refresh, повтор після втрати відповіді, replay після grace, logout, access після відкликання, незалежність іншої сесії, нормалізацію email та rollback реєстрації при збої профілю. Розгортання Render, browser recovery, password reset і перевірка міграції на production-подібних даних залишаються окремими наступними кроками.
