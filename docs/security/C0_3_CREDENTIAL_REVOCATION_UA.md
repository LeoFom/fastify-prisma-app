# Coffeo: відкликання історичних доступів — C0.3

Дата перевірки: 24.11.2026. **Оновлення після рішення власника:** MongoDB вирішено видалити; відкликання Nodemailer власник підтвердив 24.11.2026, решту відкликань відкладено. Фактичне видалення MongoDB не підтверджене. Повторна перевірка й очищення `main` виконані в [коміті 920d8de](https://github.com/LeoFom/fastify-prisma-app/commit/920d8def8f22349697bdd6bfd8160b4ede63cd75). Повне відкликання доступів не підтверджене. Поточний [звіт C0.3](C0_3_STATUS_UA.md) має пріоритет щодо статусу; нижче збережено інструкцію на випадок подальшого відкликання.

## Що знайдено і що перевірено

Публічний історичний `src/config/env.ts` у `main` API до очищення містив наведені нижче категорії. Значення, назви облікових записів і адреси серверів тут навмисно відсутні. Перевірка виконана без спроб автентифікуватися старими доступами.

| Категорія                             | Поля старого файлу                        | Необхідна дія власника                                                                          |
| ------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------- |
| MongoDB Atlas: користувач і пароль БД | `MONGO_URI`                               | Видалити непотрібного database user або змінити його пароль і оновити споживачів                |
| Поштовий доступ Gmail                 | `NODEMAILER_EMAIL`, `NODEMAILER_PASSWORD` | Відкликати відповідний пароль застосунку; email є ідентифікатором, а не секретом                |
| Ключі підпису токенів                 | `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | Переконатися, що старі ключі ніде не використовуються; замінити в усіх старих активних сервісах |
| Стара локальна PostgreSQL             | `DB_PASSWORD`, `DATABASE_URL`             | Якщо стара БД/роль існує або пароль повторно використаний — змінити відповідний пароль          |

Історичний PostgreSQL URL указує на локальний сервер, а не Neon. Параметри строку життя токенів не є секретами.

У поточному робочому коді `dev` немає MongoDB-клієнта й старого `src/config/env.ts`. Поштовий helper `src/jobs/send-mail.job.ts` читає env, але викликів helper у застосунку не знайдено. Поточна БД Coffeo — PostgreSQL. Під час початкового розгортання були створені окремі секрети; тотожність усіх поточних env старим значенням у цьому аудиті окремо не перевірялась. Якщо старий секрет був повторно внесений вручну — його потрібно замінити й там.

Актуальний конфіг `main` тепер читає env без credential literals. Попередні коміти, клони та сторонні копії цим не очищені.

Додаткова обмежена перевірка поточних файлів із Git inventory: 51 файл API і 130 файлів web (TS/JS/JSON/YAML, без lock-файлів та `.cursor`). Шаблони URI з credentials і вибраних provider tokens не дали збігів; значення не друкувалися. Це не повний secret scan: він не перевіряє всі формати ключів, історію та ігноровані env-файли й не підтверджує відкликання у провайдерів.

## 1. MongoDB Atlas

1. Увійти у [MongoDB Atlas](https://cloud.mongodb.com/) та вибрати старий project. Це користувач **бази даних**, він відрізняється від облікового запису для входу в Atlas.
2. Відкрити **Security → Database & Network Access → Database Users**. У старішому інтерфейсі розділ може називатися **Database Access**.
3. Визначити потрібного користувача приватно за старою connection string: частина перед двокрапкою у `mongodb+srv://<db-user>:<password>@<cluster>/...`. Не пересилати connection string і не вставляти її в пошук або коментарі GitHub.
4. Якщо користувач більше ніде не потрібен — видалити саме цього **database user**. Кластер і бази видаляти не потрібно. Якщо користувача використовують інші застосунки — **Edit → змінити пароль → Update User**, після чого оновити секрет у всіх таких застосунках і перевірити їхню роботу.
5. Після завершення операції перевірити зміну в Atlas та Activity Feed. Записати лише тип доступу, спосіб відкликання і дату. Якщо користувача не знайдено, перевірити правильність organization/project; це ще не підтвердження відкликання.

Документація: [керування database users MongoDB Atlas](https://www.mongodb.com/docs/atlas/security-add-mongodb-users/).

## 2. Gmail

1. Увійти саме в Google-акаунт, який використовував старий `NODEMAILER_EMAIL`.
2. Відкрити [паролі застосунків Google](https://myaccount.google.com/apppasswords).
3. Знайти пароль, створений для старого Node/Nodemailer-проєкту, та натиснути видалення/Remove. Назва могла бути довільною. Google не показує старе значення повторно, тому зіставляти його з кодом не потрібно.
4. Якщо неможливо встановити, який запис використовувався, власник може відкликати всі паролі застосунків. Це відключить інші програми, які ними користуються: їм знадобляться окремі нові доступи.
5. Переконатися, що запис прибраний. Зафіксувати дату. Новий пароль для Coffeo зараз створювати не потрібно: надсилання листів ще не підключене до потоку застосунку.

Якщо розділ недоступний, спочатку перевірити правильність акаунта та його обмеження. Зміна основного Google-пароля відкликає всі app passwords і має ширший вплив; для адресного відкликання достатньо видалення потрібного app password. [Офіційна інструкція Google](https://support.google.com/accounts/answer/185833).

## 3. Старі JWT-ключі

Це ключі самого застосунку, для них немає кнопки відкликання у провайдера.

1. Визначити, чи залишилися запущені старі інстанси API, що використовують значення зі старого файлу.
2. У кожному такому сервісі створити нові незалежні access/refresh secrets через серверні налаштування, прибрати старі ключі з перевірки токенів і перезапустити сервіс.
3. Старі токени не повинні прийматися після зміни. Користувачам цих старих сервісів може знадобитися повторний вхід. Перевірку виконувати синтетичним акаунтом у контрольованому середовищі, без виведення токенів у логи.
4. Якщо активних споживачів немає — підтвердити це як результат інвентаризації. Відсутність ключів у поточному `dev` сама по собі не доводить відсутність стороннього старого deployment.

## 4. Стара локальна PostgreSQL

1. На комп'ютері, де раніше запускали Coffeo, перевірити наявність старого PostgreSQL/контейнера та відповідної ролі. Це не поточний Neon.
2. Якщо роль досі існує — під'єднатися адміністратором саме до старого локального кластера. У `psql` можна виконати `\password old_role_name`, замінивши `old_role_name` на свою роль. Новий пароль вводиться за запитом, а не як текст SQL чи аргумент командного рядка.
3. Оновити локальні env інших програм, якщо вони користуються тією самою роллю. Якщо цей пароль повторно використаний в іншому сервісі, замінити його і там окремим унікальним паролем.
4. Якщо старий кластер і роль уже видалені та повторного використання немає — записати саме такий результат. Не видаляти БД з даними заради виконання цього пункту.

[Офіційна документація PostgreSQL про `\password`](https://www.postgresql.org/docs/17/app-psql.html) пояснює, як уникнути відкритого пароля в історії команд та серверному журналі.

## GitHub та критерії завершення

Literals із поточної `main` прибрані; не зливати старий конфіг у `dev`. Для очищення історії потрібне окреме рішення й координація всіх клонів, бо переписуються SHA. Видалення literals не відкликає доступ, тому провайдерська ротація залишається окремою дією.
